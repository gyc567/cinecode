# 上下文与修改协议（约束性）

聊天里的每条消息都会重读整个聊天。主聊天保持简短，再用文件给全新的助手代理做简报，无论片子要花多少轮，每一步都能保持小巧、快速、便宜。这些规则适用于 **Film 模式**，从第一条消息到最后一条意见轮次，在任何配置档下都一样。Quick 模式是快车道：它的主聊天自己构建、渲染并修改自己，研究在后台跑，只有预测测试、重叠检查、旁白录制，以及每一稿的独立观众才交给助手，简报格式见 §1（`quick-mode.md` §6）。

## 1. 薄协调者

主聊天是**协调者兼构建者**。它和用户对话，维护 `STATE.md`，写 `notes/round-N.md`，并承担那些它已经握有上下文的工作：短片的路线图、剧本与分镜表，画面本身以及它的修改。全新助手是冷启动（大约 60 K token，外加动手前几分钟的阅读），所以只有在划算时才把一部分活交给它：

- **独立且可并行：** 这一部分在主聊天工作旁边跑，不用等它：画面在做的时候做声音设计、录旁白、查素材或档案资料、独立观众。
- **大块：** 长片（超过约 60 s）里本章的章节，且本聊天没读过相关文件；或者任何在本聊天已经变大之后出现的工作（守卫报告 160 K token）。
- **绝不：** 上下文完全在本聊天手里的工作（3 秒片的路线图、剧本或分镜表）、脚本能回答的检查（计数、校验、测量：直接跑工具），以及五处以内定点修改。
- **工作量决定人手：** 短片或单镜头片（低于约 60 s）：只要本聊天，外加背景观众；更长的片子：本聊天加上为独立部分配的助手，最多同时三个，各自管自己的文件。独立的部分同时开始，绝不一个接一个。
- 它不读不需要的大文件、日志、代码或全尺寸图片；长参考资料按章节读。
- **共享文件只有一个主人：** `STATE.md`、`shots.json`、`audio/mix.json` 和 `LICENSES.csv` 只由主聊天写。助手只写它简报里给它的文件（`WRITES`），并报告共享文件应该改什么；守卫同时管住两边。
- **助手的话不是证据：** 它的报告要写明跑了什么命令、结果是什么；主聊天在任何关卡前自己跑那项决定性检查（`make.py check`、`make.py draft`）。
- **观众的裁决：** APPROVE、FIX（红色项：任何终稿前先修好）或 UNVERIFIABLE（它看不清或测不了决定性的东西；这一点要告诉用户）。打磨永远不开启新一轮。同一红色项出现两轮 FIX：在第三轮之前先找出原因（简报不清、方法错了、缺工具）并改变做法；只有在需要用户做决定或补材料时才找用户。
- 聊天里只留**决定和文件路径**。细节留在文件里。
- 给协调者看的图片：**每个关卡最多一张缩小的 contact sheet**（`qc.py sheet` / `qc.py thumb … 768`，一百万像素以下）。助手也只看小图（每轮 ≤ 4 张）。
- **小意见就留在这里：** 在本聊天还不到约 160 K token（守卫没报告聊天变大）时，最多五处定点修改的意见（一个颜色、一个常数、一个 cue 时间、一个词）由协调者自己做掉，然后跑一次渲染或检查。全新助手起手就约 60 K token 且还得先读文件，所以更大的活，或者本聊天已经变大时，才划算。
- **助手小而短：** 一个任务，**最多 25 次工具调用**，不带聊天历史。需要更多的任务要拆开；触到上限的助手写出 `review/<task>-handoff.md`（已完成、剩余、下一步具体动作），由一个全新助手接着做。在 Claude Code 里，该技能的守卫（`scripts/guard.py`）强制这个上限，拒绝超过 1.2 百万像素的图片，并在聊天超过 160 K 与 260 K token 时提醒协调者交接。
- 没有子代理的工具：同样的文件纪律，一个聊天一个任务，以及每个关卡一次交接（§4）。

### 简报（从文件构建，绝不从聊天历史）

`python3 tools/brief.py <kind> --task "<one line>" --writes "<its own files>" --reads "<what it reads first>" --done "<measurable: frames, numbers, qc checks>" --out logs/brief-<task>.md`（`brief.py list` 会列出各种 kind）会构建它，并把工具包针对该 kind 的规则原文引在文件里；整个文件就是助手的 prompt，开头是它打印出来的模型，守卫会拦住没有模型就启动的 Film 模式助手。`--reads` 只列这个任务真正需要的：`STATE.md` 里的 "Resume here"、`shots.json` 里该镜头那一行、`notes/round-N.md` 里涉及它镜头的那一节、一节参考资料、它要改的引擎那几行。回复进聊天（不超过 10 行）；其余都留在它写的文件里。

## 2. 意见协议

1. **逐字保存。** 用户的意见原封不动写进 `notes/round-N.md`（每轮一个文件），带上时间戳，以及给出的镜头 id。缺时间戳或缺镜头 id 的意见，一次性打包问清。
2. **按镜头拆分。** 在逐字块下面，协调者写出拆分表：意见 id · 时间 · 镜头 · 层次（画面 / 文本 / 声音 / 节奏）· 动作 · 模型 · 状态。它明确列出**未改动的镜头**。
3. **派发。** 五处以内的定点修改由协调者自己做（§1）；超出这个数，每个涉及的镜头派一个全新子代理（文本意见和声音意见各自一个）。互不影响的镜头并行跑；重 GPU 渲染在机器上一次只跑一个。每份简报只引用该镜头的那一行和它的意见小节。
4. **受影响的镜头之外的绝不碰：** 不改、不重渲染。只重编改动过的镜头，然后重新拼接。
5. **逐条回复意见，**每条一行：done / done differently because… / open because…。新的版本文件；旧版本只在用户确认终稿之后清理（`SKILL.md` Hard rules：versions without clutter）。
6. **范围变化就是重做计划。** 增加镜头或场景、或改变总时长的意见，不按镜头拆分：更新路线图和分镜表，把新计划连同每个新增或改动镜头的一张静帧给用户看，得到同意后重新开工。Quick 模式下，重做计划不占用那两轮修改机会中的任何一轮。

```markdown
# Notes round 2 · reviewed: renders/film-v1.mp4 · <date>
## Keep
- <what the user praised and must stay as it is, or "none">
## Verbatim
<the user's message, unchanged>
## Split
| Id | Time | Shot | Layer | Action | Model | Status |
|---|---|---|---|---|---|---|
| N1 | 0:12 | S04 | picture | sky two stops darker (look param) | fast | open |
Unchanged: S01 S02 S03 S05 S06
```

## 3. 先诊断，再重建

任何缺陷（几何、爆炸或其他 VFX、反射、屏幕方向、节奏、音频）：

1. **廉价复现。** 助手在缺陷处渲染 1–3 个测试帧（`capture.mjs --start <f> --end <f>`），或做测量（`qc.py`、`ffprobe`、该帧记录下来的参数值），并写 `review/diag/<shot>-<issue>.md`：症状、帧、**根因**（导致它的参数或代码行）、最小的修法、置信度、修法的成本。
2. **修最小的那个东西。** 先调参数，再改局部代码，整镜重建放最后。重新渲染同样那几个测试帧、对比，然后再渲染镜头区间。
3. **不盲目重试：** 失败的修法在下一次尝试前要重新诊断；下一个助手拿到的是诊断文件，绝不是上一个失败助手的聊天记录。
4. **同一问题的第二次重建需要用户同意，**并且要先把预估成本说清楚（§6）。

常用的第一批测量：几何 → 该帧的位置和法线，一次不做后期的调试渲染；VFX → seed、粒子数量、发射原点和 3 帧上的时间曲线；反射 → 环境贴图、粗糙度和金属度，一帧只渲反射；方向 → 逐帧的相机朝向和主体朝向，对照镜头之前的状态；节奏 → 帧号对照 `shots.json`、`qc.py cuts`；音频 → 每个时间窗的响度，起音时刻对照帧号。

## 4. 会话交接

协调者在**每个关卡**更新 `STATE.md` 的 **"Resume here"** 区块（阶段、已通过的关卡、未处理的意见、下一步动作、至今的预算），聊天变长时也要更新：大约**每 15 条用户消息**之后，或守卫报告聊天变大时（`python3 tools/usage.py --now` 负责测量）。然后保存快照（`tools/snapshot.py`），并提出 `templates/HANDOFF.md` 里的交接问题：★ "Yeni sohbette devam et"（在新会话里继续）/ "Continue in a new chat"（在新会话里继续），它会自己开启那个新会话（桌面版：`mcp__ccd_session__start_session`；其他地方：`python3 tools/handoff.py`），或者 "Burada devam et"（就在这里继续）/ "Continue here"（就在这里继续）。

新会话先读 `STATE.md`（先读 "Resume here"），然后只读它点名的文件，然后接着干。它永远不需要旧会话。

## 5. 模型

每个助手启动时都带着**指定的模型**，就是 `brief.py` 打印的那个（"start it with: model …, effort …"）：那些靠品味和判断力定输赢的工作（画面、剧本、路线图、声音设计、音乐、独立观众、修改）跑在聊天自己的模型上（`inherit`）；渲染旁白录制和找素材跑 `sonnet`；移动和列举文件跑 `haiku`。计数、校验和测量是脚本的事（`make.py`、`qc.py`、`validate_shots.py`），绝不交给助手。没带模型启动的助手会跑在聊天的模型上，那是成本最高的；守卫会记下这一点。用户可以指定别的模型；`STATE.md` 会记下来。

- **Cursor：** 不带模型的 Task/subagent 调用会跑在聊天的模型上；`.cursor/agents/*.md` 里的自定义子代理可以设置 `model:`。
- **Claude Code：** Agent 工具默认跑在会话的模型上，除非传了 `model`；agent 文件里可以设置 `model:`（`inherit` 表示沿用会话的模型）。交接用一个新会话（或 `/clear`）。

## 6. 预算表

`STATE.md` 保留**配置档的以词计上限**（Economy / Balanced / Quality）和**每个阶段的预估运行成本**。协调者在每个关卡根据助手的回复更新它。

- **按 token 计：** `python3 tools/usage.py`（Claude Code：这整部片子的每个聊天及其助手）或该工具的用量页面。一次运行的成本 ≈ 轮数 × 它的平均上下文，再加它的输出：上下文大小是那个乘数，因为每一轮都会重读整个聊天（全新助手每轮重读几万 token，长聊天则是几十万）。
- **看负载，不看原始 token：** `usage.py` 打印每个聊天的**负载**：每一轮按自己的模型加权，缓存读写按各自的费率计算，其中 1 相当于一段典型的 30 秒 Quick 片子。原始 token 总量大多是缓存读取，说明不了什么。负载是给工具包自己用的预算：绝不向用户引用金额、API 价格或美元数字（订阅制不是那样计费的）；用时间说话，用户问「还剩多少」时用片子数量说话。
- **真实片子上测得（负载）：** Quick 20 s ≈ 0.4，30 s ≈ 1，60 s ≈ 0.8 到 1.2，120 s ≈ 1.1；Film 模式的几分钟纪录片 ≈ 10 到 17。
- **60 s 以内片子的内部上限**（主聊天和助手合计，按负载计）：Economy ≈ 0.3 · Balanced ≈ 0.7 · Quality ≈ 1.3；更长的片子每多一分钟再加大约其中的一半。随片子实测结果用 `usage.py` 重新校准。
- **达到某个阶段份额或总量的 80%：** 停下来问用户（简化、接受一个明说的超支，还是砍范围）。
- **在任何整镜重建**或同一问题的第二次重建之前：说明预估成本（粗略数字，标明是估算，以及它占上限的比例），然后等用户同意。

## 7. 协调者每一轮的清单

- [ ] 工作按 §1 的分工落地：本聊天处理它握有上下文的部分，独立部分或章节交给全新子代理（文件简报、调用预算）。
- [ ] 意见逐字保存在 `notes/round-N.md`；只派发受影响的镜头。
- [ ] 缺陷在重建之前先用测试帧诊断过。
- [ ] 聊天里只有决定和路径；每个关卡最多一张 contact sheet。
- [ ] `STATE.md` 的 "Resume here" 和预算表是当前的；在关卡或聊天变长时提供交接。
